# V1.1 Note — Default Browser Launch

Status: Converted into REQ-009 for Mini Server v1.1

Authority: `requirements/active/REQ-009-default-browser-launch.md`, the current architecture, and approved decisions are authoritative if they differ from this historical planning note.

This note records the planning context that led to the approved browser-launch requirement for Mini Server v1.1.

It is not part of the Mini Server v1.0 implementation scope and must not change the completed v1.0 Edge-launch behavior.

## Current v1.0 Behavior

Mini Server v1.0 explicitly targets Microsoft Edge on Windows.

After Mini Server has started successfully, the browser-launch logic constructs the local application URL from:

    127.0.0.1
    the actual active server port
    the configured start target

Example:

    http://127.0.0.1:51847/example/

Mini Server v1.0 then locates the normally installed Microsoft Edge executable and requests Edge to open that URL.

This behavior remains the v1.0 implementation and should not be retroactively changed as part of the v1.0 release.

## Proposed v1.1 Change

Mini Server v1.1 should no longer explicitly select Microsoft Edge.

Instead, Mini Server should always request that Windows open the local Mini Server URL using the user's configured default web browser.

The intended behavior is therefore:

    Mini Server URL ready
        -> ask Windows to open the URL
        -> Windows uses the configured default browser

There is no Edge-first behavior and no browser fallback chain.

Mini Server should not need to determine whether Edge, Chrome, Firefox, or another browser is installed.

The user's Windows browser configuration determines which application handles the URL.

## Browser Independence

Mini Server should not contain browser-specific startup logic in v1.1.

In particular, normal v1.1 startup should not:

- search for `msedge.exe`;
- inspect Microsoft Edge installation directories;
- require Microsoft Edge to be installed;
- prefer Edge over another browser;
- maintain a list of supported browsers;
- implement separate launch logic for Edge, Chrome, Firefox, or other browsers;
- fall back from one explicitly selected browser to another.

Mini Server only provides the local HTTP URL.

Windows is responsible for selecting the application associated with that URL.

## First Start

When Mini Server starts a new local server instance successfully:

1. The server binds to `127.0.0.1`.
2. TCP port `0` is requested.
3. Windows assigns an available local port.
4. Mini Server obtains the actual active port.
5. The HTTP server becomes ready.
6. Valid runtime state is published.
7. Mini Server constructs the local application URL.
8. Mini Server asks Windows to open that URL using the configured default browser.

Example:

    http://127.0.0.1:51847/example/

The browser-launch request must occur only after the server URL is valid and usable.

## Repeated Start

The same browser-independent behavior applies when Mini Server is already running.

A repeated start should:

1. detect the existing local Mini Server instance;
2. obtain its valid active port;
3. construct the correct local application URL;
4. ask Windows to open that URL using the configured default browser;
5. terminate the repeated-start process normally.

The repeated start must not:

- start another HTTP server;
- request another TCP port;
- replace valid runtime state;
- depend on Microsoft Edge being installed.

## Browser Launch Failure

Failure to open the Windows default browser must not invalidate or terminate an otherwise successfully running Mini Server instance.

A browser-launch failure must not:

- stop the server;
- invalidate runtime state;
- change the active port;
- start another server;
- modify persistence data.

The complete local URL must remain available so that the user can open it manually.

Example diagnostic:

    Mini Server started on 127.0.0.1:51847

    The default browser could not be opened.

    Open this URL manually:

    http://127.0.0.1:51847/example/

A browser-launch failure is a convenience failure, not a server failure.

## Server Lifetime

The browser does not own the Mini Server process.

Closing:

- the Mini Server browser tab;
- one browser window;
- all browser windows;
- the default browser application

must not intentionally terminate the active Mini Server Java process.

The server continues running independently until the Java process itself terminates.

## Interaction with Start Sites

Mini Server v1.1 may also introduce the separately planned configurable start-site list.

If multiple start sites are configured, every generated Mini Server URL should use the same default-browser launch mechanism described in this note.

For example:

    startpage
    notes
    dashboard

may result in requests to open:

    http://127.0.0.1:<active-port>/startpage/
    http://127.0.0.1:<active-port>/notes/
    http://127.0.0.1:<active-port>/dashboard/

Mini Server should request that Windows open these URLs.

The configured Windows default browser determines how they are presented, including whether they appear as tabs, windows, or within an already running browser process.

Mini Server does not need to control that behavior.

## Architectural Intent

The v1.1 browser-launch responsibility should be reduced to:

    construct valid Mini Server URL
        +
    request operating system to open URL

Browser selection belongs to Windows and the user's operating-system configuration.

This keeps Mini Server independent from individual browser products and avoids unnecessary browser detection and installation-path handling.

The change must not alter:

- loopback-only server binding;
- dynamic port allocation;
- local single-instance coordination;
- runtime-state handling;
- persistence behavior;
- application routing;
- server lifetime.

## Scope Boundary

This change is intended for Mini Server v1.1.

Mini Server v1.0 remains based on the already implemented Microsoft Edge launch behavior.

The v1.0 implementation should not be modified merely to anticipate this future change.

This note has been converted into the appropriate:

- requirement;
- architecture update;
- technical decision;
- implementation task.

The approved v1.1 implementation may replace the browser-specific Edge launcher with an operating-system default-browser launch mechanism according to REQ-009.

The exact Windows API or Java mechanism used to request opening the default browser should be selected during implementation preparation.

The details described here remain historical planning context and are not the authoritative v1.1 implementation contract.
