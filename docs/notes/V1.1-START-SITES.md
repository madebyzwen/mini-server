# V1.1 Note — Configurable Start Sites

Status: Converted into REQ-010 for Mini Server v1.1

Authority: `requirements/active/REQ-010-configurable-start-sites.md`, the current architecture, and approved decisions are authoritative if they differ from this historical planning note.

This note records the planning context for an idea deliberately postponed until after the Mini Server v1.0 release and now approved through REQ-010.

It is not part of the v1.0 implementation scope and must not change the current T-010 requirements or implementation.

## Motivation

Mini Server can serve multiple first-level applications below:

    www/

In a future version, the user should be able to define which of these applications are automatically opened in Microsoft Edge when Mini Server is started.

The server itself continues to serve all valid applications below `www/`.

The configuration controls only which application URLs are opened automatically in browser tabs.

Applications that are not listed remain available through Mini Server but are not opened automatically.

## Proposed Configuration

Use a simple text file outside the web root, for example:

    config/start-sites.txt

The configuration should intentionally avoid key/value syntax, numbered properties, or other unnecessary configuration syntax.

Each non-empty configuration line contains only one first-level application directory name.

Example:

    startpage
    notes
    dashboard

If these directories exist below `www/`, Mini Server should request Microsoft Edge to open:

    http://127.0.0.1:<port>/startpage/
    http://127.0.0.1:<port>/notes/
    http://127.0.0.1:<port>/dashboard/

The actual active Mini Server port must always be used.

The order of entries in `start-sites.txt` determines the requested browser-opening order.

## Proposed Configuration Rules

- One application directory name per line.
- Empty lines are ignored.
- Lines beginning with `#` may be used as comments.
- Entries refer only to first-level application directories below `www/`.
- Full URLs are not accepted.
- Arbitrary filesystem paths are not accepted.
- `_shared` is reserved and must never be opened as an application.
- `example` has no special hard-coded treatment.
- The example application is opened only if `example` is explicitly listed.
- Duplicate entries should result in only one browser tab being requested for that application.
- If a configured application directory does not exist below `www/`, the entry is silently ignored.
- No browser tab is opened for a configured application that does not exist.
- A missing configured application does not prevent Mini Server from starting.
- A missing configured application does not prevent remaining valid configured applications from being opened.
- An empty configuration means Mini Server starts normally without automatically opening any application tabs.

## Example with Missing Applications

Given:

    config/start-sites.txt

containing:

    startpage
    notes
    dashboard

and the following web root:

    www/
    ├── _shared/
    ├── example/
    ├── startpage/
    └── dashboard/

the configured `notes` application does not exist.

Mini Server should therefore ignore that entry and open only:

    http://127.0.0.1:<port>/startpage/
    http://127.0.0.1:<port>/dashboard/

No tab is opened for:

    /notes/

The missing directory does not cause startup to fail.

## Application Discovery

The configuration is not intended to define which applications Mini Server serves.

Mini Server continues to determine available applications from the actual directories below:

    www/

The start-site configuration only selects a subset of those existing applications for automatic browser opening.

Adding an application to `www/` therefore makes it available through Mini Server without requiring an entry in `start-sites.txt`.

An entry is required only when that application should also be opened automatically during startup.

## Example Application

The maintained:

    www/example/

application remains part of the Mini Server distribution.

It should not receive special browser-launch logic.

For normal productive use, `example` can simply be omitted from:

    config/start-sites.txt

If a developer wants the example application to open automatically, the configuration can explicitly contain:

    example

This avoids introducing a separate configuration option such as:

    openExample=false

and keeps all automatically opened applications governed by the same mechanism.

## First Start

When no active Mini Server instance exists in the current local user/computer context, the future startup flow should conceptually be:

1. Start Mini Server normally.
2. Bind to `127.0.0.1`.
3. Request port `0`.
4. Obtain the operating-system-assigned port.
5. Confirm that the server is ready.
6. Publish valid runtime state.
7. Read `config/start-sites.txt`.
8. Validate each configured application name against the actual first-level directories below `www/`.
9. Ignore entries whose application directory does not exist.
10. Construct URLs for the remaining valid configured applications using the actual active port.
11. Request Microsoft Edge to open those application URLs.

The browser-opening step must not influence whether the applications themselves are served by Mini Server.

## Repeated Start

If Mini Server is already running in the current local user/computer context, a repeated start should:

1. Recognize the active Mini Server instance.
2. Reuse the existing server process.
3. Obtain the active instance's existing port from valid runtime state.
4. Read `config/start-sites.txt`.
5. Validate the configured application names against the current `www/` directory.
6. Ignore configured applications whose directories do not exist.
7. Construct URLs for the remaining configured applications using the existing active port.
8. Request Microsoft Edge to open those application URLs.
9. Terminate the repeated-start process without starting another HTTP server.

A repeated start must not request another port or start another server instance.

## Browser URL Construction

Configured entries contain only application directory names.

For an entry:

    dashboard

and an active Mini Server port:

    51847

the resulting URL is:

    http://127.0.0.1:51847/dashboard/

Users must not need to enter:

- the protocol;
- the loopback address;
- the port;
- leading slashes;
- trailing slashes;
- complete URLs.

Mini Server constructs the complete local URL automatically.

## Failure Behavior

The start-site configuration is a browser convenience feature and must not become a prerequisite for running Mini Server.

A missing application directory is therefore not an error.

It is simply ignored.

If some configured applications exist and others do not, all existing configured applications should still be opened.

Mini Server should continue running even if no configured application can be opened.

A browser-launch failure must also not invalidate an otherwise successfully running Mini Server instance.

## Security and Scope

The configuration must not allow arbitrary filesystem paths or arbitrary URLs.

Configured values represent only first-level application directory names below:

    www/

The mechanism must reuse the existing application-path validation and security model wherever appropriate.

The configuration does not provide authentication, authorization, or application isolation.

Its only purpose is to select which already available Mini Server applications should be opened automatically in the browser.

## Scope Boundary

This feature is intentionally postponed until Mini Server v1.1.

Mini Server v1.0 should be completed using the already approved startup and browser-launch design.

Do not modify T-010 or the active v1.0 requirements in order to implement this feature.

No v1.0 implementation work should be expanded because of this note.
