# REQ-004 — JavaScript Client API

## Requirement ID

REQ-004

## Title

JavaScript Client API

## Status

Active

## Purpose

Mini Server must provide a shared browser-side JavaScript library that gives hosted web applications a simple interface to the central JSON persistence API.

Application developers must be able to work with native JavaScript objects, arrays, and values without manually implementing HTTP requests or JSON serialization.

## Description

A shared JavaScript library named:

    mini-api.js

must be provided centrally at:

    www/_shared/mini-api.js

Hosted applications can include it using:

    <script src="/_shared/mini-api.js"></script>

The library must expose a global API object named:

    MiniApi

The public interface for v1.0 is:

    MiniApi.readSection(section)
    MiniApi.readAll()
    MiniApi.write(data)
    MiniApi.removeSection(section)
    MiniApi.clear()

These method names are part of the public MiniApi contract.

The library acts as the browser-side abstraction over the server's persistence API.

Application code should normally use MiniApi rather than constructing persistence API requests directly.

## Asynchronous Contract

All MiniApi operations are asynchronous and return native JavaScript Promises.

The public methods therefore return:

    Promise

A Promise resolves only when the corresponding server operation has completed successfully.

A Promise rejects when:

- Client-side validation fails
- The HTTP request cannot be completed
- The server returns a non-successful HTTP status
- A JSON response expected from the server cannot be processed correctly

Application code may use normal Promise handling or `async` / `await` where supported by the target browser environment.

MiniApi must use one consistent asynchronous model for all public operations.

## Site Detection

The library must determine the current application site automatically from the browser URL.

For example:

    http://127.0.0.1:<port>/example/index.html

results in the site namespace:

    example

Requests generated by MiniApi from that page therefore target:

    /example/api/

Application code must not normally need to configure or provide the site name.

The site namespace must be derived from the current page URL.

Application code must not provide an arbitrary filesystem path or persistence location to MiniApi.

### Security Scope

Automatic site detection is a convenience and scoping mechanism.

It is not authentication or authorization.

Applications hosted by one Mini Server instance normally share the same HTTP origin.

MiniApi automatically targets the current application's namespace during normal use, but deliberately written JavaScript may still send direct HTTP requests to another valid application's API namespace without using MiniApi.

Mini Server v1.0 does not use MiniApi as a security boundary between hosted applications.

Applications hosted together by one Mini Server instance are considered part of the same trusted local environment.

## readSection

The method:

    MiniApi.readSection(section)

must read one named section from the current application's persistence data.

It sends:

    GET /<site>/api/read?section=<encoded-name>

The section name must be URL-encoded by MiniApi.

If the operation succeeds, the returned JSON value must be deserialized and the Promise must resolve with the corresponding native JavaScript value.

For example:

    const settings = await MiniApi.readSection("settings");

If the stored section contains:

    {
        "theme": "dark"
    }

then `settings` is the native JavaScript object representing that value.

A stored JSON null value is valid.

Therefore:

    await MiniApi.readSection("example")

may successfully resolve to:

    null

when the section exists and contains JSON null.

A missing section causes the Promise to reject with the error information returned by the server.

## readAll

The method:

    MiniApi.readAll()

must request:

    GET /<site>/api/readAll

If the operation succeeds, the returned JSON root object must be deserialized and the Promise must resolve with that native JavaScript object.

Example:

    const data = await MiniApi.readAll();

If the site's persistence file does not yet exist, the server returns:

    {}

and MiniApi resolves with an empty JavaScript object.

## write

The method:

    MiniApi.write(data)

must create or replace one or more sections in the current application's persistence data.

The caller passes a native JavaScript object whose top-level properties represent sections.

Example:

    await MiniApi.write({
        settings: {
            theme: "dark",
            language: "en"
        }
    });

Multiple sections may be written in one operation:

    await MiniApi.write({
        settings: {
            theme: "dark"
        },
        favorites: [
            "Search A",
            "Search B"
        ]
    });

MiniApi must serialize the supplied object to JSON internally.

The caller must not need to call:

    JSON.stringify()

before calling `MiniApi.write()`.

The request must use:

    POST /<site>/api/write

with an appropriate JSON request content type.

The write input must be a non-null, non-array JavaScript object containing at least one own top-level property.

The top-level property names must satisfy the Mini Server section-name rules.

Values must be representable as valid JSON.

A successful server response is:

    204 No Content

When that response is received successfully, the Promise resolves with:

    undefined

MiniApi must not require or invent a success response body.

## removeSection

The method:

    MiniApi.removeSection(section)

must remove one named section from the current application's persistence data.

It sends:

    DELETE /<site>/api/remove?section=<encoded-name>

The section name must be URL-encoded by MiniApi.

Example:

    await MiniApi.removeSection("settings");

A successful server response is:

    204 No Content

When the operation succeeds, the Promise resolves with:

    undefined

If the requested section does not exist, the server returns `404 Not Found` and the Promise must reject.

## clear

The method:

    MiniApi.clear()

must request:

    DELETE /<site>/api/clear

A successful server response is:

    204 No Content

When the operation succeeds, the Promise resolves with:

    undefined

Clearing an already empty persistence store is successful.

Clearing a site whose persistence file does not yet exist is also successful.

## JSON Handling

MiniApi must perform JSON serialization and deserialization internally.

For normal API use, application developers must not need to call:

    JSON.stringify()

or:

    JSON.parse()

themselves.

`readSection()` and `readAll()` convert successful JSON responses into native JavaScript values.

`write()` converts the supplied native JavaScript object into the JSON request body.

`removeSection()` and `clear()` do not expect a response body after a successful `204 No Content` response.

## Client-Side Validation

MiniApi must validate clearly invalid calls before sending a request where practical.

Section names supplied to:

    MiniApi.readSection(section)
    MiniApi.removeSection(section)

must follow the section-name rules defined by the API contract.

A valid section name:

- Contains between 1 and 128 characters
- Is not empty
- Has no leading whitespace
- Has no trailing whitespace
- Contains no control characters

Unicode characters and normal characters such as spaces, hyphens, underscores, and periods may be used inside a section name.

`MiniApi.write(data)` must reject input when:

- `data` is null
- `data` is an array
- `data` is not an object
- `data` contains no own top-level properties
- A top-level property name is not a valid section name
- The supplied data cannot be represented as valid JSON

Client-side validation must remain generic.

MiniApi must not interpret application-specific business rules.

## Error Handling

MiniApi must not silently convert failed operations into successful results.

When the server returns a non-successful HTTP response, the corresponding Promise must reject.

The server's standard API error format is:

    {
        "error": {
            "code": "SECTION_NOT_FOUND",
            "message": "Section not found."
        }
    }

When such a response is available, MiniApi must preserve the machine-readable error code and human-readable message for the calling application.

The rejected error exposed by MiniApi must provide, where available:

- HTTP status
- Server error code
- Human-readable message

The exact internal JavaScript error implementation may be chosen during implementation, but these values must remain accessible to application code.

Network failures or malformed unexpected server responses must also cause rejection rather than being reported as successful operations.

Browser-facing errors must not introduce or expose unnecessary filesystem details.

## HTTP Contract

MiniApi must use the server API defined by D-017:

    GET    /<site>/api/read?section=<name>
    GET    /<site>/api/readAll
    POST   /<site>/api/write
    DELETE /<site>/api/remove?section=<name>
    DELETE /<site>/api/clear

MiniApi must not substitute different HTTP methods for these operations.

Successful JSON-returning operations expect:

    200 OK

Successful modifying operations expect:

    204 No Content

A non-successful HTTP status must result in a rejected Promise.

## Application Independence

The shared library must not contain application-specific business logic.

It must work for any valid first-level application below the Mini Server web root.

Adding another application must not require creating a modified copy of `mini-api.js`.

The library must not expose arbitrary filesystem paths or allow application code to override the persistence filesystem location derived by the server from the requested site namespace.

## Acceptance Criteria

REQ-004 is fulfilled when all of the following are true:

- A shared `www/_shared/mini-api.js` file exists.
- Multiple hosted applications can use the same library.
- The library exposes the global `MiniApi` interface.
- The public methods are `readSection`, `readAll`, `write`, `removeSection`, and `clear`.
- Every public MiniApi operation returns a Promise.
- Requests generated by MiniApi are automatically scoped to the current application's API namespace.
- `MiniApi.readSection(section)` uses the server's GET read endpoint.
- `MiniApi.readSection(section)` resolves with the native JavaScript representation of the stored section value.
- A stored JSON null value can be returned successfully by `readSection`.
- Reading a missing section rejects the Promise.
- `MiniApi.readAll()` uses the server's GET readAll endpoint.
- `MiniApi.readAll()` resolves with the complete native JavaScript persistence object.
- `MiniApi.write(data)` uses the server's POST write endpoint.
- `MiniApi.write(data)` can write one section.
- `MiniApi.write(data)` can write multiple sections in one operation.
- `MiniApi.write(data)` accepts native JavaScript objects.
- `MiniApi.write(data)` rejects invalid or empty write input before sending where practical.
- A successful `write()` resolves with `undefined` after receiving `204 No Content`.
- `MiniApi.removeSection(section)` uses the server's DELETE remove endpoint.
- A successful `removeSection()` resolves with `undefined`.
- Removing a missing section rejects the Promise.
- `MiniApi.clear()` uses the server's DELETE clear endpoint.
- A successful `clear()` resolves with `undefined`.
- Section names are URL-encoded correctly.
- Section-name validation follows the server API contract.
- JSON serialization is performed internally.
- JSON deserialization is performed internally.
- Application developers do not normally need `JSON.stringify()` or `JSON.parse()` for MiniApi operations.
- Server-side API errors remain visible to the calling application.
- Rejected API errors expose the HTTP status, server error code, and message when available.
- Network failures reject rather than appearing successful.
- One shared library works for all hosted applications.
- The library contains no application-specific business logic.

## Constraints

The client library must remain small and dependency-free unless a later approved decision changes this.

It should use browser-native functionality where practical.

The library must remain compatible with the intended Microsoft Edge target environment.

The library must not expose arbitrary persistence filesystem paths.

The implementation must follow the API contract defined by D-017.
