# REQ-004 — JavaScript Client API

## Requirement ID

REQ-004

## Title

JavaScript Client API

## Status

Active

## Purpose

Mini Server must provide a shared browser-side JavaScript library that gives hosted web applications a simple interface to the central JSON persistence API.

Application developers should be able to work with normal JavaScript objects and arrays without manually implementing HTTP requests or JSON serialization.

## Description

A shared JavaScript library named:

mini-api.js

must be provided centrally below the shared web root area.

The intended location is:

www/_shared/mini-api.js

Hosted applications should be able to include the library using:

<script src="/_shared/mini-api.js"></script>

The library must expose a global API object named:

MiniApi

The intended interface is:

MiniApi.read(section)
MiniApi.readAll()
MiniApi.write(data)
MiniApi.remove(section)
MiniApi.clear()

The library acts as the browser-side abstraction over the central server API.

## Site Detection

The library must determine the current application site automatically from the browser URL.

Example:

    http://127.0.0.1:<port>/example/index.html

must result in the site scope:

    example

API requests generated by the library must therefore target:

    /example/api/

Application code should not normally need to configure or provide the site name manually.

The site namespace used by MiniApi must be derived from the current page URL rather than from an arbitrary filesystem path or persistence location supplied by application code.

### Security Scope

Automatic site detection is a convenience and scoping mechanism.

It is not an authentication or authorization mechanism.

Applications hosted by one Mini Server instance normally share the same HTTP origin.

MiniApi automatically targets the current application's namespace during normal use, but deliberately written JavaScript may still send HTTP requests to another valid application's API namespace without using MiniApi.

Mini Server v1.0 does not attempt to use MiniApi as a security boundary between hosted applications.

Applications hosted together by one Mini Server instance must therefore be considered part of the same trusted local environment.

## read

MiniApi.read(section)

must request one named section from the current site's persistence API.

Example:

MiniApi.read("settings")

must logically call:

/<site>/api/read?section=settings

The returned JSON value must be converted into the corresponding native JavaScript value before being returned to application code.

## readAll

MiniApi.readAll()

must request the complete JSON data for the current site.

The returned JSON data must be converted into native JavaScript objects, arrays, and values before being returned to application code.

## write

MiniApi.write(data)

must allow application code to create or replace one or more named sections.

Application code must pass normal JavaScript objects and arrays.

The caller must not need to call JSON.stringify() before using MiniApi.write().

The library must perform the required JSON serialization internally.

The interface must support writing a single section as well as multiple sections in one operation.

Example logical usage:

MiniApi.write({
    settings: {
        theme: "dark",
        language: "en"
    }
})

Multiple sections must also be supported:

MiniApi.write({
    settings: {
        theme: "dark"
    },
    favorites: [
        "Search A",
        "Search B"
    ]
})

The exact internal HTTP payload format is an implementation detail.

## remove

MiniApi.remove(section)

must request removal of one named section from the current site's data.

Example:

MiniApi.remove("settings")

must logically call:

/<site>/api/remove?section=settings

## clear

MiniApi.clear()

must request that the current site's stored JSON data be reset to an empty state.

It must not require application code to know the location of the site's data file.

## JSON Handling

The shared library must perform JSON serialization and deserialization internally.

For normal API use, application developers must not need to call:

JSON.stringify()

or:

JSON.parse()

themselves.

The public API should work with native JavaScript values.

## Validation

The library must perform basic validation before sending API requests.

At minimum, it should detect clearly invalid calls such as:

- Missing required section names
- Empty or invalid section names where a section is required
- Invalid write input
- Unsupported values that cannot be represented as valid JSON

Validation must not attempt to interpret application-specific business rules.

## Error Handling

API errors must be made available to the calling application.

The library must not silently convert failed server requests into successful results.

The exact error object structure may be standardized during implementation.

Errors should provide enough information for application code and developers to determine whether an operation failed.

## Asynchronous Operation

API calls involve HTTP communication and must therefore be usable asynchronously.

The public interface should use a consistent asynchronous programming model.

The exact implementation style may be finalized during implementation while remaining compatible with the project's supported browser environment.

## Application Independence

The shared library must not contain application-specific business logic.

It must work for any valid first-level web application below the Mini Server web root.

Adding another application should not require creating a modified copy of mini-api.js.

## Acceptance Criteria

REQ-004 is fulfilled when all of the following are true:

- A shared www/_shared/mini-api.js file exists.
- Multiple hosted applications can use the same library.
- The library exposes MiniApi as its browser-side interface.
- MiniApi.read(section) can read one section.
- MiniApi.readAll() can read all data for the current site.
- MiniApi.write(data) can write one section.
- MiniApi.write(data) can write multiple sections in one operation.
- MiniApi.remove(section) can remove one section.
- MiniApi.clear() can clear the current site's data.
- The current site is detected automatically from the browser URL.
- Requests generated by MiniApi are automatically scoped to the current application's API namespace.
- Application code does not normally need to provide the site name.
- Application code can pass native JavaScript objects and arrays to the API.
- JSON serialization is performed internally.
- JSON deserialization is performed internally.
- Application developers do not normally need JSON.stringify() or JSON.parse() for API operations.
- Basic invalid input is detected before sending requests where practical.
- Server-side API errors remain visible to the calling application.
- The library contains no application-specific business logic.
- One shared library works for all hosted applications.

## Constraints

The client library should remain small and dependency-free unless a later approved decision changes this.

It should use browser-native functionality where practical.

The library must remain compatible with the intended Microsoft Edge target environment.

The library must not expose arbitrary filesystem paths or allow application code to override the persistence filesystem location derived by the server from the requested site namespace.
