# Release v1.0

## Status

Planned

## Purpose

Version 1.0 is the first functional release of Mini Server.

The goal of this release is to provide the complete initial Java implementation for lightweight local or internal web applications.

The release must establish the stable core concept of the project without introducing unnecessary additional functionality.

## Target Environment

The initial release targets:

- Windows
- Java 8 compatible runtime
- Microsoft Edge
- Local loopback operation through 127.0.0.1

The server is not intended for public internet use.

## Included Requirements

Version 1.0 is planned to include the following active requirements:

- REQ-001 — Static File Serving
- REQ-002 — Dynamic Port Allocation
- REQ-003 — JSON Persistence API
- REQ-004 — JavaScript Client API
- REQ-005 — Example and Template Applications
- REQ-006 — Startup and Browser Launch
- REQ-007 — Error Handling and File Permissions
- REQ-008 — Runtime and Distribution

All acceptance criteria required for these requirements must be reviewed before the release is marked complete.

## Planned Functionality

Version 1.0 should provide:

- A lightweight Java-based HTTP server
- Java 8 compatibility
- Static file serving from the www directory
- Multiple independent web applications below the shared web root
- Automatic allocation of an available local TCP port
- Binding to 127.0.0.1 for normal local operation
- Automatic Microsoft Edge launch
- A central JSON persistence API
- Per-application JSON data files
- Isolation between application data
- A shared mini-api.js browser library
- Native JavaScript object and array handling through MiniApi
- A working example application
- A reusable template application
- Predictable error handling
- Operation without administrator privileges
- Deployment without a separate database, application server, or web server

## Planned Distribution Structure

The initial release should provide a compact distribution similar to:

mini-server/
├── mini-server.jar
├── www/
│   ├── _shared/
│   │   └── mini-api.js
│   ├── example/
│   └── template/
└── startup files

The final filenames and packaging details may differ if required by the implementation.

The fundamental runtime structure and behavior must remain consistent with the approved requirements and architectural decisions.

## Release Verification

Before version 1.0 may be released, the following must be verified:

- The project builds successfully.
- The produced application is compatible with Java 8.
- The application starts successfully on the intended Windows target environment.
- The server binds to 127.0.0.1.
- The operating system dynamically assigns the server port.
- The actual assigned port is used for the browser URL.
- Microsoft Edge opens the configured start application.
- Static files are served correctly.
- Path traversal outside the web root is prevented.
- Multiple application directories can be served.
- Each application uses its own JSON data file.
- Each application's normal API usage is scoped to the persistence file belonging to the site namespace addressed by the request.
- All required JSON API operations function correctly.
- mini-api.js works from multiple applications.
- Application code can use native JavaScript objects and arrays directly.
- The example application works end to end.
- The template application works end to end.
- File permission failures are handled correctly.
- Invalid JSON and malformed API requests are handled correctly.
- Startup errors do not result in an invalid browser launch.
- Relevant automated tests pass.
- No active acceptance criterion required for v1.0 remains knowingly incomplete.

## Release Procedure

When all version 1.0 requirements are fulfilled:

1. Verify all acceptance criteria.
2. Complete the end-to-end release verification.
3. Update CHANGELOG.md.
4. Change this release status from Planned to Released.
5. Record the release date.
6. Move fulfilled requirement files from requirements/active/ to requirements/archive/v1.0/.
7. Update requirements/INDEX.md.
8. Update tasks/ACTIVE.md so completed v1.0 tasks are no longer presented as active work.
9. Review README.md and other documentation against the actual release.
10. Create the version control release and tag only when explicitly approved.

## Archived Requirements

After the release, the completed requirements should be stored under:

requirements/archive/v1.0/

The archived requirement documents should preserve the released v1.0 behavior and should not later be rewritten to describe newer versions.

Future changes to released functionality should be represented by new requirements.
