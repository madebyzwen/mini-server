# Release v1.1

## Status

Planned

## Purpose

Mini Server v1.1 is the next planned minor release after v1.0.0.

It adds Windows-default-browser opening, Shared/Private start-site selection, an interactive first-run and manual reselection experience, and a unified current-user storage hierarchy with safe migration of released v1.0 Private data.

## Approved Requirements

The complete approved v1.1 functional scope is:

- REQ-009 — Default Browser Launch
  - Mini Server asks Windows to open local URLs through the configured operating-system HTTP handler instead of selecting Microsoft Edge.
- REQ-010 — Configurable Start Sites
  - Shared installation configuration defines current eligibility and order for automatic opening. Private current-user configuration may reduce but never elevate or reorder Shared. Missing Private configuration is initialized from current valid Shared, and the built-in root page supports fresh replacement selection.
- REQ-011 — Unified Current-User Storage
  - Current-user Mini Server configuration and Private application data use separate `Config` and `Data` areas below `%APPDATA%\MiniServer`, with safe migration from the released v1.0 Private persistence location.

All three requirements remain active under `requirements/active/` and target v1.1.

## Approved User Experience

The v1.1 distribution remains planned to include `example` as the default active entry in Shared `<installation-root>\config\start-sites.txt`. The application is not hard-coded in Java.

The first normal start action without a Private file initializes `%APPDATA%\MiniServer\Config\start-sites.txt` from only the current valid normalized Shared applications in Shared order. It then opens only `http://127.0.0.1:<active-port>/` through the Windows-default-browser mechanism.

`GET /` provides the English-only `Welcome to Mini Server` page. It derives all choices from current valid Shared configuration, initially selects all of them, never uses Private as checkbox-state input, and clearly presents saving as replacement of the complete personal selection. A later manual visit to `/` provides the same intentional reset/reselection workflow.

The loopback-only `POST /__miniserver/start-sites` route rereads current Shared at save time, filters untrusted requested membership to that current valid set, preserves Shared order, and safely replaces the Private file. Empty selection is valid. Saving applies on the next normal start action and does not open applications immediately.

When Private already exists, normal first and repeated starts continue to open the current valid Shared/Private intersection in Shared order and do not automatically open `/`.

## Approved Storage Transition

Canonical v1.1 current-user paths are:

```text
%APPDATA%\MiniServer\Config\start-sites.txt
%APPDATA%\MiniServer\Data\<site>\data.json
```

Shared persistence remains:

```text
<installation-root>\www\<site>\data\data.json
```

Local runtime coordination remains:

```text
%LOCALAPPDATA%\MiniServer\runtime\
```

The released v1.0 Private persistence path `%APPDATA%\MiniServerData\<site>\data\data.json` is a migration source only. An existing canonical file wins. Otherwise, legacy content is migrated safely before normal Private use, and legacy data is removed only after canonical establishment. Migration failure preserves legacy data; there is no permanent dual-write or fallback model.

## Compatibility Boundary

The following behavior remains authoritative unless an active v1.1 requirement explicitly refines it:

- Loopback-only binding to `127.0.0.1`
- Operating-system-assigned dynamic ports
- Local per-user/computer single-instance coordination
- Detached `javaw.exe` startup
- Authenticated graceful `stop.bat` shutdown
- Static multi-application serving and direct application URL access
- Explicitly scoped Shared and Private JSON persistence API
- MiniApi and persistence concurrency behavior
- Shared persistence location
- Browser-independent server lifetime
- Java 8 compatibility

Start-site configuration and the built-in selection page remain browser conveniences, not application discovery, static-serving, authentication, authorization, or access-control mechanisms.

## Scope Boundary

No additional v1.1 feature is approved by this document. New functionality requires its own approved requirement and must not be inferred from planning notes or roadmap ideas.

REQ-009, revised REQ-010, REQ-011, the current architecture, and approved decisions are authoritative if earlier planning or completed pre-refinement implementation differs.

## Release Verification

Version 1.1 must not be marked ready or released until T-018 is implemented and final T-017 verification reviews every active v1.1 acceptance criterion plus the required v1.0 regressions. Earlier T-017 Phase 1 evidence from the pre-refinement implementation remains historical context only and must be rerun after T-018. A known incomplete required criterion prevents release readiness.
