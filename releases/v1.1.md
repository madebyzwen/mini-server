# Release v1.1

## Status

Planned — not release-ready

## Purpose

Mini Server v1.1 is the next planned minor release after v1.0.0. It adds
Windows-default-browser opening, Shared/Private start-site selection, the D-030
setup/editing/recovery and immediate-apply UX, a supported configure action,
and a unified current-user storage hierarchy with safe migration of released
v1.0 Private data.

## Approved Requirements

The complete approved v1.1 functional scope remains exactly:

- REQ-009 — Default Browser Launch
- REQ-010 — Configurable Start Sites, as refined by D-030
- REQ-011 — Unified Current-User Storage

All three requirements remain active under `requirements/active/` and target
v1.1. No additional feature is approved by this release document.

## Approved D-030 User Experience

### Normal Start

After readiness and actual dynamic-port publication, normal start behaves as:

```text
missing Private
    -> root setup only; no Private creation

readable Private with at least one effective Shared intersection
    -> open applications in Shared order

zero, stale, unreadable, or unavailable effective selection
    -> root recovery only
```

Closing first-run setup without saving commits nothing and causes a later
normal start to offer setup again. Existing Private selections do not gain
newly Shared applications automatically.

### Root State

`GET /` always derives available choices and order from current valid Shared.
Missing Private checks all choices only as an unsaved proposal. Readable Private
checks its current valid intersection. Unreadable Private warns that saved state
could not be read and guesses no selection. Private never introduces a choice
outside Shared.

Readable Shared with no valid applications and unavailable Shared are distinct
explanatory recovery states. Neither creates Private, permits saving, or opens
an application automatically.

### Save and Open

A saved selection must contain at least one current valid Shared-approved
application. Empty and save-time-normalized-to-empty requests fail without
changing existing Private. The server rereads Shared, normalizes membership,
deduplicates, restores Shared order, and safely writes the canonical Private
file.

Only after that write succeeds, the normalized selection applies immediately.
The success result contains server-normalized applications and server-generated
local targets. The root tab navigates to the first target and additional targets
open in order; raw request values never determine URLs. Double submission is
suppressed. Browser failure does not roll back the selection, stop the server,
or block isolated later attempts.

### Supported Reconfiguration

The distribution contains `configure.bat`, invoking dedicated configure
mode. It starts the normal detached loopback/dynamic-port server when absent or
reuses the active instance and actual port when present, starts no duplicate
server, opens only `/` through the Windows default browser, and modifies no
Private configuration itself. Browser failure leaves the server active.

## Approved Storage Transition

Canonical v1.1 current-user paths are:

```text
%APPDATA%\MiniServer\Config\start-sites.txt
%APPDATA%\MiniServer\Data\<site>\data.json
```

Shared persistence remains
`<installation-root>\www\<site>\data\data.json`, and local runtime coordination
remains `%LOCALAPPDATA%\MiniServer\runtime\`.

The released v1.0 Private persistence path
`%APPDATA%\MiniServerData\<site>\data\data.json` is a migration source only. An
existing canonical file wins. Otherwise, legacy content is migrated safely
before normal Private use and removed only after canonical establishment.
Migration failure preserves legacy data; there is no permanent dual-write or
fallback model.

## Compatibility Boundary

The following remain authoritative:

- loopback-only binding to `127.0.0.1` and operating-system dynamic ports;
- local per-user/computer single-instance coordination;
- detached portable Windows startup and authenticated graceful shutdown;
- Windows default-browser launch and browser-independent server lifetime;
- static multi-application serving and direct valid application URLs;
- explicitly scoped Shared and Private persistence, MiniApi, and concurrency;
- Shared persistence and local runtime-state locations; and
- Java 8 compatibility.

Start-site configuration and root UI remain browser conveniences, not
application discovery, static-serving, authentication, authorization, or
access-control mechanisms.

## Release Verification

v1.1 is not release-ready. Revised REQ-010 and D-030 are implemented and local
automated/build/distribution verification is complete, but manual Windows
verification must be rerun against the packaged result. T-018 remains Planned
until that work passes. T-017 must then verify every active criterion and
required v1.0 regression against the post-D-030 implementation.

No release date is assigned. Earlier T-017 Phase 1 evidence and the pre-D-030
Windows attempt are historical context only. A known incomplete criterion
prevents release readiness.
